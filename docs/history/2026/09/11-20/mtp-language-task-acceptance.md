# MTP採用率のGPU・言語・タスク比較（2026-09-11）

## 結論

V620の採用率がR9700より一貫して低い、という仮説は今回の測定では成り立たなかった。36組の同一prompt/seed比較はV620<R9700が17組、V620>R9700が16組、同率3組。提案tokenを合算した全体はV620 2617/3930 = 66.59%、R9700 2628/3919 = 67.06%で、差は約0.47 percentage pointsだった。小規模な探索的比較であり、有意差・同等性や普遍的なGPU順位を主張しない。

## 条件

Qwen3.8 27B NVFP4、BF16 companion、MXFP8 E4 KV、固定T=1/P=.95/K20、MTP幅2、single GPU/batch1。現行source `c27e346d5f3332d6e8ce794b7913b87c42455c99` のgfx1030/gfx1201 serverを、481 source hashとbinary hashを照合して使用した。checkoutは記録追加のみの `094495c9`。

英語・日本語・中国語×コード生成／推論／要約／創作の12 prompt、seed 123/456/789、各最大128出力。各GPUで別promptのwarmup 1要求を行い、その後36要求を同じresident serverへ逐次送信した。両GPUも順次実行した。全72測定要求は128 tokenを生成し、finish_reason=length。自然な入力長は62〜176 tokenで、GPU間の同一prompt token数は一致した。今回のコード課題はPythonであり、プログラミング言語間の比較ではない。

直前の8192/128 coding速度基準とは別suite。短い出力予算なので、回答途中までの採用率を測っており、最終回答の正答率・完遂率を評価していない。翻訳による長さや語彙の差は残るため、自然言語の因果効果も主張しない。

## 解釈・安全な比較範囲

- 同じprompt/seedでも全36組で生成本文が異なった。APIはtoken ID列を返さないため、ここで確認したのは本文UTF-8 hashの不一致である。各GPUが進んだ生成履歴も異なるので、率の差にはその後の文脈差が含まれる。
- GPU別kernel・数値経路は差の候補だが、本比較で原因を特定していない。V620の精度が低い、R9700がBF16へ近い、とは結論できない。
- 両GPUとも全37要求（warmup込み）がHTTP 200、実HIP、CPU fallbackなし、非zero dispatch、MTP提案あり、accepted+rejected=proposed。要求解放後request-state/workspaceは0、shutdownのcurrent/request-state/workspace/retryable/durableも0。
- process終了直後のsysfsはVRAM解放途中を捕捉した。後続確認でV620はidleと約17 MBへ戻った。runtime allocationの解放とsysfsの即時値を同一視しない。R9700の既存serviceは元のunit/script/binary不変で復帰し、health/ready HTTP 200を確認した。
- エンジン実装は変更していない。Phase84の量子化前後比較ではGPUごとにBF16 companionを基準にし、今回のような同一prompt/seedの組を使う。両GPUの採用率を一致させることは受入条件に追加しない。
