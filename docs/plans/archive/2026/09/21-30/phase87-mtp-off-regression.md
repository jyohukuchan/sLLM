# Phase 87: 段階5後のMTPなし速度低下

## 依頼と受入条件

2026-09-21のユーザー依頼により、MTPなしの速度低下を調査する。
MTPあり高速化との不可避なトレードオフと確認できた場合に経路を分ける。
因果確認前に不可避と決めつけず、共通の改善で解消できる場合はそれを優先する。

- 同じモデル、8192入力／128出力、固定sampling、warmup 1回＋測定3回で両GPUを比較する。
- 起動時費用、定常decode、profiler自身の費用を区別する。
- MTPなしの低下を解消し、MTPありの改善を維持する。
- N0、状態の数値一致、EOS／budget後の非公開、非同期replay、cleanupを維持する。
- 変更対象の検証を行う。過去に完了した帯域調査や無関係なGPU検証は再開しない。

## 調査と実装

1. 段階5最終バイナリを凍結し、同一バイナリのlegacy／whole graphと保存済み段階5前バイナリを再測定する。
2. 保存profileのGDN状態選択コピーを調査する。コピーのkernel時間だけで全体の因果を断定しない。
3. 有効generationの奇偶による状態バッファ交互利用を共通経路へ実装する。
   全prefix採用時のコピーを除き、MTP部分採用時は選択checkpointを次の状態へ反映する。
4. 奇数／偶数generation、余分なNoop、停止と部分採用の状態をeagerと比較する。
5. 通常性能と固定出力一致、必要なprofileを確認し、結果に基づいて経路分割の要否を判断する。

## 切り分けで分かったこと

- 保存済み段階5前バイナリを再実行し、R9700のMTPなし21.3965 token/sを確認。
  現行同一バイナリはlegacy 20.6546、whole graph 20.8695 token/sであり、
  単なるwhole graph無効化では速度は戻らない。
- 旧／現行legacyの新規profileでは、attention stage1とmergeのgrid／回数は同一。
  kernel時間は合計で約1.6763 ms/token増加し、通常測定の約1.6787 ms/token増加とほぼ一致した。
  graph対応で追加した動的split数が、定数除算と定数上限loopの最適化を妨げた可能性を検証する。
- このため、上記の状態コピー削減に加え、attentionのP32／P128切替後の計算を
  定数templateへ戻す共通修正を実施する。切替境界と演算順序を維持する。
- whole graphの状態選択コピーはlegacyには存在しない。両者の原因を混同しない。
- 共通修正後、V620のMTPなしは16.0744 token/sで低下を解消したが、R9700は21.3271で
  旧21.3965に約0.3%届かなかった。merge時間は復元できた一方、controlled stage1には差が残る。
  全モデルの反復計測を増やす前に、対象stage1のcodegenと小さな性能probeで残差を調べる。
- profileでは最後の破棄replayにも約43 msかかっていた。残り1出力と確定した場合のみ
  不要な後続replayを予約しない修正を追加する。その他の先行実行とEOS時の破棄は維持する。
  公開前の終端検証と実際に予約したreplay数に基づく監査をfocused host testで確認する。
